## What it is

A **DSH (DeepSeek Harness) plugin** that turns a **real WeChat alt account** into your "secretary": you send it text or files on WeChat, it does the work on your computer (look things up, edit files, run commands, tidy things up) and replies on WeChat.

It is **not** a chatbot and **not** a customer-service bot: no group auto-replies, no marketing scripts, no payments or transfers. It serves only the whitelisted owner (by default, just you). The goal is to take as little of your attention as possible while getting things done.

**Important: this repository does NOT include the "bridge"** (the WeChat client automation layer). The bridge logs into WeChat, sends/receives messages and downloads attachments — that part touches UI automation and is easily targeted by the platform, so it is not published. You provide your own bridge. This project only defines the **HTTP contract** and the host-side orchestration (DSH plugin + Secretary preset).

## Features

- **Per-chat queue**: one serial queue per WeChat chat; the cursor advances only after a message is handled successfully; failures retry a bounded number of times, then the entry is skipped and logged. No duplicate delivery.
- **Backlog merge**: messages accumulated while the host or bridge was offline are kept per chat across polling rounds; once the backlog is old enough and large enough (default: older than 10 minutes and at least 3 messages) it is merged into one summary, with attachments numbered inline in order. Below the threshold, messages are handled one by one and marked as "N minutes old".
- **Two reply modes**: no "on it!" receipt by default; a task that takes longer than `slowNoticeSec` (default 180 s) sends a short progress note, then reports every `progressEverySec`. Final answers can be `raw` or `summary` (a few condensed sentences) via `reflowMode`.
- **Cross-session dispatch**: `wechat_secretary_sessions` lists DSH sessions in the same workspace; `wechat_secretary_dispatch` supports `queue` (hand off a task; queued if the session is busy) and `steer` (interject; off by default). Before dispatching it checks whether the target session is stuck (`turn/end blocked`) and refuses with an explanation if so.
- **Memory and mood**: `plugin/memory.js` is plain files, zero dependencies — owner profile, facts with validity ranges (so it can answer "what did you say last time"), task ledger, daily summaries; retrieval scores by keyword hit × time decay × importance with an injection budget. Mood is a hidden tag at the end of an answer, stripped before sending, and only affects tone — never facts.
- **Approval and cancellation**: the secretary session runs with approval policy `never` (you cannot tap native approval popups from a phone), so dangerous actions are blocked by a hard `tools.guard` (delete files, install/uninstall plugins, change system settings, write outside the workspace, outbound writes). To proceed, the secretary asks you on WeChat via `wechat_secretary_approve`; approval grants a 10-minute one-shot pass. Sending 停 / 停止 / 取消 / 别做了 on WeChat cancels the running task.
- **Self-healing**: after a DSH restart the plugin probes the local bridge and may try to start it (`autoStartSidecar`, off by default — you must configure paths). A separate bridge watchdog gives up after 5 consecutive failures and logs loudly.
- **Ledger and observability**: `workitems.jsonl` records every work item (received / working / waiting_human / done / dropped / failed); `GET /wechat-secretary/workitems` serves a read-only summary from the DSH host.

## Install and configure

### 0. Prerequisites

- Windows with a WeChat PC client logged into your alt account (prefer a dedicated machine or VM that only has the alt account);
- **Your own bridge** implementing the four endpoints below, reliably sending/receiving text and files;
- DSH (DeepSeek Harness) desktop app able to install local plugin bundles.

### 1. Install the two bundles

- `plugin/`: the channel plugin (host half, always resident — polling, dispatch, replies, ledger, memory).
- `preset/`: the Secretary preset (persona + tool surface + red lines). It provides the `secretary` mode.

Install each directory as a bundle (or insert the rows from its `cordis.patch.yml` into your profile's `cordis.patch.yml`), then enable them. Create a new session and pick the **Secretary** mode.

### 2. Bridge HTTP contract (defined here, implemented by you)

```
GET  /health
  → { "ok": true, "self": { "nickname": "…", "username": "…" },
      "uptime_s": 123, "polls": 456, "errors": 0, "reply_enabled": true }

GET  /inbox?since=<seq>&limit=<n>
  → { "entries": [ {
        "seq": 1, "chat": "wxid_xxx", "sender": "wxid_xxx",
        "type": "text", "content": "…",
        "create_time": 1790000000, "detected_at": "2026-01-01T10:00:00+08:00",
        "latency_s": 37.2,
        "files": [ { "name": "a.pdf", "path": "C:/…/a.pdf", "size": 12345 } ]
      } ], "nextSeq": 2 }

POST /send   { "chat": "wxid_xxx", "text": "…", "file": "optional local path", "requestId": "optional idempotency key" }
  → { "ok": true, "display": "remark name", "readback": true, "messageId": "optional" }
  Errors: 403 not whitelisted; 409 busy; 503 WeChat not logged in / unavailable

POST /typing { "chat": "wxid_xxx" } → { "ok": true }
```

The bridge must distinguish messages **to** the alt account from messages **from** it (do not echo-loop its own sends) and deduplicate on the WeChat local message id.

### 3. Plugin configuration (`plugin/cordis.patch.yml`)

| Key | Meaning |
|---|---|
| `bridgeUrl` | bridge URL, default `http://127.0.0.1:8710` |
| `cwd` | workspace where the secretary does its work (required; replace `<YOUR_WORKSPACE>`) |
| `whitelist` | only these chat ids are processed (put yours; replace `wxid_master`) |
| `agentPreset` | preset used when creating sessions, default `secretary` |
| `statePath` | state file, default `data/plugin-state.json`; `workitems.jsonl` and `memory/` live next to it |
| `slowNoticeSec` / `progressEverySec` | slow-task notice and progress reporting (0 = off) |
| `stopWords` | cancellation words, comma separated |
| `hardGuard` | hard-block dangerous commands (keep `true`) |
| `permissionPreset` | DSH permission preset for the secretary session (default `danger-full-access`; dangerous actions are still gated by the hard guard + WeChat approval) |
| `memory` | memory/mood switches and budgets; empty `dir` = `memory/` under the plugin data directory |
| `device` | device-side (phone runtime) interface, off by default — see "Device-side interface" below |
| `autoStartSidecar` | try to auto-start the local bridge (default `false`; also requires `sidecarPythonPath` and `sidecarScriptPath`) |

### 4. Safety notes

- Log in the alt account only; keep only the owner in its contacts; whitelist only the owner. Never automate your main account.
- Never commit the bridge, WeChat data directories or state files to a public repo (this repo's `.gitignore` already ignores `data/` and `*.log`).
- Platform terms and risk control are your responsibility. This project contains nothing that circumvents platform limits.

## Known limitations

- **No bridge included**: without a bridge there is no I/O. The contract is simple, but WeChat client automation is sensitive to client updates and must be maintained by you.
- **Latency**: messages are discovered by polling, typically 30–40 s before they enter the queue. Fine for "dispatch a task, get a result", bad for real-time chat.
- **Groups and payments**: no group listening/auto-replies, no payments, transfers, red packets or account settings.
- **Approval**: native DSH approval cannot be tapped from a phone, so the design is "policy never + hard guard + remote approval over WeChat". `steer` is off by default.
- **One alt account, one machine**: WeChat itself allows an account on one PC at a time; multi-machine setups need their own switching story.
- **Text send** relies on the bridge's read-back verification; if your bridge cannot read back, trust its return value.

## Device-side interface

The `device` section describes an optional phone-side runtime (used when the PC is offline). It is off by default and not implemented here. Expected endpoints:

```
GET  /health  → { deviceId, app, version, capabilities, wechat, battery, charging, wifi, queue, uptime_s }
GET  /inbox?since=&limit=  → { items: [ { seq, chat, sender, type, content, files, create_time, detected_at } ], nextSeq }
POST /send    { chat, text?, file?, requestId? } → { ok, readback, messageId }
POST /typing  { chat } → { ok }
```

Rules: heartbeat ~30 s; offline fallback after ~60 s; only whitelisted chats; never touch payments; no broadcasts.
